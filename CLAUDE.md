# monitor-input

Switches a monitor's input source over DDC/CI from a tray / menu bar icon or global hotkeys.
Replacement for ASUS DisplayWidget, which has no hotkeys and no macOS version.

All code, comments, commit messages and repo docs are in English. The owner talks in Ukrainian.

## Hardware

* Monitor: ASUS ROG Swift **PG32UQ**, EDID id `AUS32E1`, DDC/CI enabled in the OSD.
* Inputs advertised in its capabilities string (`60(11 12 0F)`): DisplayPort `0x0F`, HDMI 1 `0x11`, HDMI 2 `0x12`.
* Windows PC is on DisplayPort; the Mac is on one of the HDMI ports.
* The monitor accepts DDC/CI only from the input currently on screen, so each machine switches *away* from itself.
  Testing on one machine means: switch the picture to it first (from the other machine or the OSD).

## How switching works

VESA MCCS VCP code `0x60` (Input Source), written over the DDC/CI I2C channel (7-bit address `0x37`).
Write packet after the `0x51` host sub-address: `84 03 60 <hi> <lo> <chk>`, chk = `0x6E ^ 0x51 ^` all packet bytes.
Read: write `82 01 60 <chk>`, wait >= 40 ms, read 11-12 bytes: `6E 88 02 <rc> 60 <type> <maxH> <maxL> <curH> <curL> <chk>`.

ASUS DisplayWidget (by Portrait Displays, `C:\Program Files\Portrait Displays\ASUS DisplayWidget`) was checked:
`DisplayWidget.exe` imports `SetVCPFeature` / `GetVCPFeatureAndVCPFeatureReply` from `dxva2.dll`, and its
`ui/html/main.html` uses the standard values (15 DP, 16 DP2, 17 HDMI1, 18 HDMI2, 19/20 USB-C, 83/84 HDMI3/4).

## Windows (`windows/`) - done, tested on the PG32UQ

* `MonitorInput.cs` - single C# 5 source (no tuples / string interpolation: built by the .NET Framework 4.x `csc.exe`).
  * CLI (`monitor-input.exe`): `list`, `get`, `set <input>`, `set dp,hdmi1` (cycle), `-m <selector>`.
  * Tray (`/define:TRAY`, `monitor-input-tray.exe`): left click opens `InputPicker` (a button per advertised input,
    active one bold with a dot, plus a "Sleep display" button: `WM_SYSCOMMAND`/`SC_MONITORPOWER` posted to the
    hidden hotkey window after 500 ms so the mouse-up doesn't wake it); right click menu; global hotkeys via `RegisterHotKey` from `monitor-input.ini`
    next to the exe; "Start with Windows" toggles `HKCU\...\Run\MonitorInputTray`.
  * Capabilities take ~1 s to read, so the picker warms its cache at startup and opens instantly.
  * DDC calls retry: reads 5x100 ms, writes 3x50 ms, capabilities 3x.
* `build.cmd` builds in place; `install.cmd` stops the running copy, builds, installs to `%LOCALAPPDATA%\MonitorInput`,
  registers autostart and launches it; `uninstall.cmd` reverses that.
* `app.ico` is generated by `icon/make-icon.ps1` (monitor with blue screen and white switch arrows, 16-256 px,
  all entries 32-bit DIB because `csc /win32icon` and `System.Drawing.Icon` reject PNG entries).
* `.cmd` files must have CRLF line endings.

Default hotkeys: `Ctrl+Alt+1` DP, `Ctrl+Alt+2` HDMI 1, `Ctrl+Alt+3` HDMI 2.

## macOS (`mac/`) - done, tested on the PG32UQ (M1 Mac mini: built-in HDMI and a USB-C -> HDMI adapter)

* `main.swift` - Apple Silicon only. DDC via the private `IOAVServiceCreateWithService` / `IOAVServiceWriteI2C` /
  `IOAVServiceReadI2C` (same approach as MonitorControl and m1ddc). Displays are found by walking the IOService plane:
  an `AppleCLCD2` / `IOMobileFramebufferShim` node (its `DisplayAttributes.ProductAttributes` give name and vendor)
  followed by its `DCPAVServiceProxy` with `Location = External`.
  * CLI: `list` (with model and advertised inputs), `get`, `set <input>`, cycle, `-m <selector>` - same as Windows;
    `login-item on|off|status` (works only when run from inside the .app, used by the install scripts).
  * Capabilities: `F3` request loop in 32-byte chunks, ~1.5 s; `MonitorInfo` parses `model(...)` and `60(...)`.
  * `tray` (or launching `MonitorInput.app` without arguments): menu bar agent (`NSStatusItem`, accessory policy).
    Left click opens `InputPicker`, an `NSPopover` with a button per advertised input (current one bold with a dot),
    capabilities warmed up at startup, plus a "Sleep display" button (`pmset displaysleepnow`); right click / ctrl+click shows the menu ("Launch at login" via `SMAppService`).
    Hotkeys via Carbon `RegisterEventHotKey` (no Accessibility permission needed), config
    `~/.config/monitor-input.conf`, default `ctrl+opt+1/2/3`. All tray DDC traffic goes through one serial queue.
  * Menu bar icon is drawn in code (`makeStatusIcon`, template image: outlined monitor with the two arrows).
  * `auto` selector falls back to a display that does not answer reads (some links are write-only).
* `build.sh` - `swiftc` + `MonitorInput.app` bundle (`LSUIElement`, `AppIcon.icns`, ad-hoc `codesign`).
  `install.sh` - builds, copies to `~/Applications`, links `~/bin/monitor-input`, enables launch at login, starts it
  (also removes the old `com.user.monitor-input` LaunchAgent); `uninstall.sh` reverses that.
* `AppIcon.icns` is generated by `icon/make-icon.swift` (`swift make-icon.swift [--preview <dir>]`),
  same geometry and colors as `windows/icon/make-icon.ps1`.

Built-in HDMI of the M1 Mac mini (registry `Transport = {Upstream=DP, Downstream=HDMI}`, an internal DP -> HDMI
converter): with chip address `0x37` the converter answers by itself - every reply is the null message `6E 80 BE`
and writes are dropped (EDID over `0x50` still reads fine). Passing `0xB7` (bit 7 set) as the chip address to
`IOAVServiceWriteI2C` / `ReadI2C` reaches the monitor; found by looking at which constants BetterDisplay passes.
`Display.read` flips between `0x37` and `0xB7` on a null message and keeps whichever answers; `switchInput` always
reads before writing so the write uses the right address. Tested on the owner's Macmini9,1: `get`, `list`
(capabilities) and `set dp` work on the built-in HDMI; `0x37` works via a USB-C -> HDMI adapter. The Mac is on
monitor HDMI 1.
